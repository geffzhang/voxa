VLS-011 — Streaming (online) speaker diarization

VLS-005 diarizes a finished recording: it collects the whole file, segments it, embeds each region, then clusters. That is the right shape for a meeting upload and the wrong shape for a live call — it needs the end of the audio to answer, re-runs the model over everything whenever the recording grows, and has no vocabulary for "this label may still change". This spec adds the online counterpart: who spoke when, as the audio arrives, with a stated lookahead, stable speaker numbers across the session, and a revision protocol so the answer can improve without the consumer re-deriving history.

Scope. Five decisions, each of which a streaming diarizer can get wrong in a way that only shows up in production: keep the speaker-level mask, keep incremental audio state instead of the recording, keep session-wide speaker state, say out loud whether a result may still change, and join the result to transcripts on one clock without running the model on the data loop. Sections 2–6 are those five, in order.

1. Problem

Three things break when a batch diarizer is pointed at a live stream.

  • It needs the future. Clustering is global: a merge decided at minute 9 can relabel minute 1, and nothing is final until the call ends. A live caption has to be publishable at minute 1.
  • It re-reads the past. Every new chunk invalidates the previous answer, so the cost of minute n is proportional to n, and memory grows with the call.
  • It answers a coarser question than the stream can ask. Speech/silence regions are enough to cut a meeting into turns; they are not enough for overlapping speech, for "who is this" across the call, or for attaching a transcript to a person.

The underlying cause is the same in all three: the batch pipeline reads the segmentation model's powerset output and immediately collapses it to speech | silence (PowersetSegmentationDecoder.FrameActivity). Everything a streaming system needs — which local speaker, how confident, whether two are talking at once — is in the powerset and is thrown away by that collapse.

2. Keep the speaker-level mask

pyannote's segmentation head emits, per 10 ms frame, one logit per powerset class: silence, one class per speaker, one per speaker pair (3 speakers × up to 2 concurrent ⇒ 7 classes). The new decode is a softmax followed by a marginal onto the local speakers:

p[s] = Σ_c softmax(logits)[c] · mapping[c][s]        // mapping = BuildPowersetMapping(...)

PowersetSegmentationDecoder.FrameSpeakerProbabilities (pure, no ONNX, unit-tested on synthetic logits) produces one probability per local speaker per frame. What that preserves:

InformationSpeech/silence collapseSpeaker-level marginal
Which local speakerlost — a hand-over becomes one regionone probability per speaker
Overlapping speechlost — one region, one labeltwo non-zero entries ⇒ two people talking
Confidencelost — binarythe value itself (onset/offset hysteresis reads it)
Voiceprint extractionimpossible — no span to embed per speakereach speaker channel gives its own span

The marginal deliberately does not sum to 1: a pair class contributes its whole probability to both of its members, because the channels are later read as independent tracks. Two channels open on one frame is the overlap signal.

Local channels are not global speakers. Channel 0 in one window is not channel 0 in the next — the mapping is arbitrary per window. So frames can never be accumulated across windows by channel. What is stable across windows is a run of frames on one channel inside one window: a local turn. The turn covers a known audio span, that span is embedded once, and the embedding is what carries identity forward.

3. Incremental audio state

3.1 The buffer

AudioRingBuffer is a fixed-capacity circular buffer addressed by absolute sample index. That addressing is the whole point: a segment, a window, and an embedding span are all expressed as indices from the session start, so dropping old audio changes what can be re-read — never what a timestamp means.

Write(samples)              // appends, evicting by capacity
CopyTo(absoluteStart, dest) // zero-fills before Oldest / past End; returns the real sample count
DiscardBefore(absoluteIndex)

3.2 The window schedule

Windows run every HopSamples (default: 10% of the window). A window is trusted only for the slice in its centre — the part both it and its neighbours saw — so the diarizer owns exactly one hop per window:

ownedStart = windowStart + (window − hop) / 2
ownedEnd   = ownedStart + hop

A turn whose end lands inside ownedEnd is final: no later window can move it. That is where the lookahead comes from, and it is exposed rather than hidden — StreamingDiarizer.CommitFrontierSeconds is the newest instant that is fully decided, and SamplesSeen − frontier is what the capability costs in latency. With the shipped pyannote geometry (5 s window, 0.5 s hop) that is 2.25 s.

3.3 Retention and eviction

Two readers need the buffer, and they reach back different distances: the window schedule needs [nextWindowStart, nextWindowStart + window), and a turn's closing embedding needs that turn's whole span. Audio is dropped only when neither can use it:

DiscardBefore(min(nextWindowStart, SamplesSeen − MaxBufferedSeconds · SampleRate))
Evicting by window start is a correctness bug, not just a memory trade. Dropping everything before the next window leaves a long turn's closing read with only its tail — a 1.5 s turn described by its last 0.1 s, which in an overlap is the other person's voice. The retention rule above is what keeps a turn's embedding about the turn; with a 60 s default, a turn longer than that is the only case that is described by part of itself.

3.4 Flush and gaps

Flush() ends the stream: it continues the same window schedule to the end with a zero-padded tail (the batch decoder's last chunk, same idea), then commits every open turn. It never steps back over audio already processed — a flush window that re-ran decided audio would see a run whose left edge is no longer the audio it started at, and would mint a second segment for a finished turn.

NotifyGap(droppedSamples) is the honest answer to lost audio (the caller's queue overflowed). The timeline still advances — a timestamp keeps meaning what it meant — but the window schedule restarts after the hole and every open turn is closed, because whatever continued inside the lost audio cannot be recovered. A gap is a discontinuity, never silently stitched.

4. Session-level speaker state

SpeakerPrototypes holds one prototype per speaker: an L2-normalised centroid, a weight that freezes at PrototypeWeightCap seconds (bounded drift over a long call), and an uncapped TotalEvidence used only for merge eligibility.

4.1 Numbering

Ids are handed out in creation order and are never renumbered or reused. The only way an id disappears is a merge, and the survivor is always the older id — so a consumer's history keeps its meaning, and a stale id always maps forward through the merge notice.

4.2 Short turns and low confidence

A turn may create a speaker only with MinNewSpeakerEvidence seconds of speech and MinTurnConfidence mean track activity. Everything thinner is adopted, never invented:

CaseResultConfidence
Creates a speakernew id1.0
Matches an existing speakerthat id1 − distance
Ambiguous (matched, in the dead band) or speaker cap reachednearest id0.5·(1 − distance)
Too thin to describe, previous speaker within ContinuityWindowborrowed id0.25
Too thin, nothing to borrowUnknownSpeaker (−1)0

The "speaker cap" row matters: hitting MaxSpeakers never renumbers anyone. A new voice attaches to the nearest prototype and says so through its confidence, which is a truthful answer; re-using an id would not be.

4.3 Enrolment is a closing read

A turn is described twice: once as soon as it carries enough audio (the provisional label — this is what low latency buys), and once when it ends, from the complete turn. Only the closing read moves a prototype (enrol: true). A provisional match returns an id but does not fold its embedding into the centroid — otherwise an overlap in progress teaches a settled speaker the other person's voice, and the error persists for the rest of the call.

4.4 Merges

Each window end, two prototypes closer than MergeThreshold are folded together — but only if the retiree's TotalEvidence is under MergeEvidence. A voice that has carried a long stretch of the conversation is never retired into a newcomer. Merges produced by a window re-publish the affected segments (same ids, higher revisions) within RevisionWindow; older history is left alone and reaches consumers through SpeakerMergedFrame.

5. May a result change?

Yes — and the shape of the answer is the point.

SpeakerSegmentUpdate(string Id, int Speaker, double Start, double End, bool IsFinal, int Revision, double Confidence)
  • An update is a keyed upsert on Id. Revision starts at 0 and only increases; a consumer that sees a lower revision than it holds ignores it.
  • IsFinal means the geometry is settled (the end will not move) — not that the label is perfect. A consumer that wants stable captions can drop provisional segments and accept a (window − hop) / 2 delay.
  • Two revision sources, both bounded: an extended end while the turn grows, and a merge relabel inside RevisionWindow. Nothing older than the window is rewritten.

5.1 The latency/accuracy contract, stated

What a consumer may assumeBound
Audio at t has a decided labelt ≤ CommittedFrontierSeconds = SamplesSeen/sr − (window − hop)/2/sr
A provisional label may still changeuntil the segment's IsFinal revision
A merge may rewrite historyonly inside RevisionWindow (default 30 s); older via the merge notice
Speaker idsstable; never reused; only a merge retires one, into a lower id
Why not decide once, later? Because the answer is needed now. The trade is made explicit twice: the early read gives a provisional label at the cost of accuracy, and the closing read gives accuracy at the cost of one extra embedding per turn. Both are published, in order, on the same id.

6. Transcript alignment and the frame pipeline

6.1 One clock

Streaming diarization owns the input clock, because it is the only stage that sees the continuous input (it sits before the VAD: diarization needs silence, the VAD gates it away). Every chunk it forwards carries its absolute start sample:

AudioRawFrame.StartSample        (long?, null = not stamped)
   ↓  STT records the utterance's first/last stamped chunk
TranscriptionFrame.StartTime/EndTime   (double?, absolute seconds)
   ↓  interval join
SpeakerSegmentFrame.Start/End          (absolute seconds)

No per-stream offset bookkeeping: a transcript and a segment are joined by overlap on one timeline. A chunk replayed by the VAD's pre-roll keeps its stamp, so the replay still points at the audio it came from.

6.2 Attributing text that crosses a speaker change

SpeakerTimeline resolves a transcript span to a speaker by:

  1. greatest total overlap, summed per speaker — so one speaker whose turn is split across several segments (a revision, a merged neighbour) is not penalised against a single competing segment;
  2. ties go to the earlier-starting segment — deterministic, and the documented answer for text that genuinely covers two speakers;
  3. nothing covers it yet — the diarizer commits behind the audio, so the span borrows the speaker whose segment ends closest before it, if that is inside ContinuityWindow.

The segment stream stays authoritative: a later revision carries the corrected label on the same clock, so any consumer can re-join history. An engine that already labels speakers (a diarizing STT) is left alone — an existing SpeakerId is never overwritten.

6.3 Never block the data loop

data loop:  AudioRawFrame → stamp → PCM16 → float → TryWrite(queue)
                                                        │ full ⇒ count as dropped (a gap, later)
                worker:  ReadAllAsync → NotifyGap? → Push → SpeakerSegmentFrame / SpeakerMergedFrame

One worker task per session owns the diarizer (which is not thread-safe by design: one instance, one consumer). The data loop only enqueues — a slow model delays diarization, never the conversation. On EndFrame the queue is completed, the worker is waited for within FlushTimeout, any remaining drops are reported as a gap, and Flush() commits the tail.

9. Known limits

  • A turn longer than MaxBufferedSeconds is described by what is retained — bounded memory, stated rather than hidden.
  • Speaker identification (enrolment against known voices) is a different problem: ids here are per-session clusters, not a directory.
  • Two speakers who only ever talk simultaneously cannot be separated by an embedding of the mix; the closing read's span may not contain a dominant frame for either. The segment still carries both channels' turns, which is what overlap detection needs.
  • Cross-session speaker memory is out of scope; the prototypes die with the diarizer.
